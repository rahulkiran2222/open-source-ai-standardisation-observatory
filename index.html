Research design

A lean path from prototype to a small empirical study.

Reproducible by design
01 / DEFINE

Scope and unit of analysis

Define the open-source AI projects, standards bodies and time period before collecting records. Write inclusion and exclusion rules first.

02 / CODE

Write the codebook

Distinguish formal membership, direct contribution, consultation response, declared alignment, contextual mention and no evidence found. Do not infer participation from topical similarity.

03 / VERIFY

Audit 5–8 relationships

For each candidate relationship, record the exact URL, source passage, access date, relationship type and decision. Keep only relationships supported by the source.

04 / ANALYSE

Describe the small network

Use a simple descriptive network to test the data workflow. With only a few verified relationships, label the graph illustrative and make no general or brokerage claims.

05 / EXTEND IF JUSTIFIED

Consider network structure

Only expand the sample or test brokerage if a literature review, adequate coverage and suitable outcome data justify that next step.

06 / REPORT

Publish transparent results

Release the verified CSV, one-page codebook, source audit, analysis notebook and limitations. Add extra engineering only when it helps research reproducibility.

Explain the project in a meeting

Use this as a briefing aid. Be explicit about what is established and what is still a research question.

30-second explanation

“I am developing an evidence-based observatory to study how open-source AI projects interact with formal standardisation and governance networks. The prototype links projects, institutions, standards and policy records, but it only labels a relationship as documented when a source supports it. My research interest is to understand which participation pathways are visible, who bridges communities and standards bodies, and where public evidence is missing. The next step is a reproducible, manually validated dataset—not an automated claim that a project is compliant.”

Questions a professor may ask

The broad relationship between open-source development and standardisation has been discussed in prior research. The proposed contribution is narrower and must be established by a literature review: a transparent, empirically coded map of open-source AI projects' documented participation pathways into AI standardisation and governance. Do not claim the topic has never been studied.
A directory lists actors. The research instrument defines units, inclusion rules, relationship categories, evidence strength, temporal scope and missingness; it supports replication, reliability checks and network analysis.
Use primary-source-first collection, store a citation for each edge, distinguish direct ties from contextual relevance, require manual verification for publication, and report uncertainty and missing data. The LLM can assist retrieval/coding but must not be the final authority.
Only that the interface and evidence model can represent a small curated set of public records. It does not yet establish a representative network, test the hypotheses, or demonstrate causal effects. Those require a larger validated dataset and a defined research protocol.
Blind's research covers standardisation, regulation, intellectual property and open-source software, including research on the interaction between open source and standard-setting. The proposed project operationalises that broad question in the open-source AI domain and uses auditable evidence to examine documented participation pathways.

The intersection is the study of how emerging AI technologies connect to institutions and innovation processes. This is a conceptual fit, not a claim that he co-supervises this project.
